# 向日葵 · 团队业绩 DApp

SUNFLOWER（`0xfd06eeAdC43ee0687D5611d698Fb2Ee39f9BAAAa`）的推荐关系与团队业绩统计。

绑定关系写在链上，业绩在链下按统一规则算出来，奖励由项目方核算后人工发放。
**合约里没有钱，也没有任何自动发奖逻辑** —— 这是刻意的，链上自动返佣被薅过。

```
contracts/ReferralRegistry.sol   绑定合约（无限层；本人绑一次，owner 可更正绑错的）
indexer/accounting.js            业绩规则引擎（纯函数，可离线验证）
indexer/index.js                 扫链 → 生成 web/report.json
tools/reconcile.js               发奖前对账：报表 vs 链上，逐地址
web/                             前端（原生 HTML/JS，零依赖，静态托管即可）
```

## 业绩怎么算

一句话：

> **业绩 = 你买入、并且还拿着的那部分代币，按买入当时的美元价计。**
> 其中「还拿着」= 钱包余额 **+** 抵押在借贷金库里的数量。

写成一条规则而不是一堆特例，是为了少犯错。所有情况自动落位：

| 发生什么 | 余额 | 抵押 | 业绩 |
|---|---|---|---|
| 在池子里买入 | ↑ | — | **计入**（按成交当时 BNB/USD） |
| 抵押借贷后买入 | ↑ | — | **计入**（和自己掏钱一样） |
| 公平铸造 | ↑ | — | **计入**（按实付 BNB，0.01515 BNB / 2500 枚） |
| 抵押给金库 | ↓ | ↑ | 不变 |
| 赎回取回 | ↑ | ↓ | 不变 |
| 卖出 | ↓ | — | **扣减**（扣成本，不是卖出价） |
| 转给别的地址 | ↓ | — | **扣减** |
| 违约被销毁 | — | ↓ | **扣减** |
| 别人转进来 / 空投 | ↑ | — | 不变 |

**为什么转账必须扣。** 不扣的话：买 $10,000 → 转到小号 → 小号卖掉 → BNB 转回来 → 再买一次。
同一笔钱无限刷业绩，成本只有买卖税。`accounting.test.js` 里跑了 5 轮这个循环，业绩始终是 0。

**成本按 FIFO 冲减。** 买 $500、涨一倍卖掉 40%，扣的是那 40% 的**原始成本 $200**，不是卖得的 $400。
全卖光业绩归零，**不会变成负数**。

**没买过的不算。** 空投或别人转进来的币成本为 0；往外转时**先消耗这些**，所以帮人过一手不会吃掉自己挣的业绩。

**一个副作用要告诉社区**：自己两个钱包之间转币也会掉业绩。链上无法区分「我的另一个钱包」和「朋友的钱包」，
任何想区分的规则都会立刻变成刷子的入口。建议后台做「钱包归并」，由项目方人工把多个地址标成同一人。

## 每一笔是怎么认定的

代币转账**按交易净额**计，不是逐条日志。税币一次买入可能搬好几次币（池子→买家、池子→税池），
聚合器还会再多几跳；一个人实际多了多少、少了多少，只有整笔交易的净变化说了算。

在此之上，有四件事不能靠"转账长什么样"去猜，每一件都在真实数据里猜错过：

| 认定什么 | 依据 | 猜会错在哪 |
|---|---|---|
| 抵押 / 赎回 / 违约 | 借贷金库自己的 `BorrowStarted` / `RepaidAndUnstaked` / `Defaulted` 事件 | 抵押可能和金库的闲置回购挤在同一笔交易里，形状上和交易税分不开，曾把一笔抵押记成卖出 |
| 铸造付了多少 | 代币自己的 `Minted(account, paidBNB, tokenOut)` 事件 | 铸造是批量结算，`msg.value` 为 0、钱直接变流动性，看转账像白送 |
| 是买入还是加池 | 池子有没有**出**币 | 加池也是 BNB 进池子；只看 BNB 就会把流动性记成某人的买入 |
| 是卖出还是撤池 | 池子有没有**进**币 | 同上，反过来 |

每个事件都和同一笔交易里的转账逐一核对（同一方、同一数额），对不上就**直接中止**，不会带着错数出报表。

这些地址的余额是协议行为，不是谁的业绩，已在 `EXCLUDED` 里排除：

| 地址 | 是什么 |
|---|---|
| `0xfd06eeAdC43ee0687D5611d698Fb2Ee39f9BAAAa` | 代币合约自己（3% 税先囤在这里再换 BNB，也是铸造的发放方） |
| `0x72861674beea6a8046e485327adac898ee2e611d` | PancakeV2 交易对 |
| `0xdda9d6c1738EA47e047b220a6FecC3cfC9d65cB6` | 借贷金库（它的闲置回购是协议行为） |
| `0xcb8c07c87a698329060e122edf383b581274c7fe` | 平台金库 |
| `0x…dEaD` / `0x0` | 销毁与铸造 |

## 取数：Alchemy 免费档就够

`RPC_URL` 指向 Alchemy 的 BSC 端点即可，不需要付费计划。

免费档的 `eth_getLogs` 限 10 块一次，直接扫是走不通的（全历史要十几万次）。绕法是：

- **转账**用 `alchemy_getAssetTransfers`，它不受 10 块限制，全部历史约 30 次调用拿完
- **事件**（抵押、铸造）只在"已知动过币的区块"上做定点 10 块扫描，约 280 次
- **价格**用归档 `eth_call` 读 Chainlink BNB/USD，按成交区块逐个读，本地缓存，第二次起几乎免费
- **推荐关系**直接读合约状态（`referrer()`），用 Multicall3 一次 400 个地址，几次调用拿完，owner 的更正自动反映

整套首次约 900 次调用，之后主要是增量。

**对账也锁在报表自己的区块高度上**，不读最新块。这个币一直在交易，拿报表去比"现在的余额"，
量出来的是中间那几分钟的新成交，不是账算得对不对 —— 曾因此把一个算对的地址看成差了 63 枚。

## 前端

原生 HTML + CSS + JS，**不加载任何库**，静态托管即可（Vercel / Cloudflare Pages / 任意 OSS）。

没有邀请链接的人，推荐人默认填 ROOT（官方），可以改成别人的地址；带 `?ref=` 来的则锁定为邀请人。
签名前会先读一次链，推荐人还没加入时直接给中文提示，不让人对着钱包报错发懵。

因为不引库，合约调用是手写编码的，四字节选择器写死在 `web/app.js` 里。
写错的选择器**不会报错**，只会安静地什么都不调 —— 所以有个检查脚本，别跳过：

```bash
node tools/check-selectors.js
```

（第一次写的时候，5 个里有 3 个是错的。）

## 合约

`ReferralRegistry` 只存：谁的推荐人是谁、直推数、成员总数。**没有资金、没有升级。**

绑定需要**本人发交易并付 gas**，所以绑定无可争议是他自己的决定；本人只能绑一次，绑后自己改不了。
成员之间，没人能替别人绑，也没人能把别人挂到自己名下 —— 唯一的例外是下面的 owner。

### owner 能做什么，不能做什么

owner 只有一项业务权限：`correctReferrer(用户, 新上级)`，用来更正绑错的推荐关系。

这个权限**要说清楚**：握有 owner 私钥的人可以把任何成员挪到任何上级下面，
而奖励是按这棵树人工核算的 —— 等于能决定谁的买单算在谁的团队里。
所以它被限制在这几条之内：

- **碰不到钱。** 合约里没有余额，也不调任何外部合约。
- **每次更正都上链留痕。** `ReferrerCorrected(用户, 原上级, 新上级)`，任何人可查。
- **可以永久放弃。** `renounceOwnership()` 之后再没有任何私钥能改关系。
- **转移要两步。** `transferOwnership` 提名、对方 `acceptOwnership` 才生效，填错地址不会丢掉权限。
- **部署者和 owner 可以分开。** 用热钱包部署、冷钱包当 owner。

### 为什么不会成环

原来"每个地址只能绑一次"本身就保证了无环。加了更正之后这个论证不再成立：
A→B 之后若把 A 改挂到 B 下面，就成了 A→B→A。

所以 `correctReferrer` 在改之前**沿新上级往上走一遍**，走到被移动的人就拒绝。
这是合约里唯一一处循环，只在 owner 更正时跑，成员绑定不受影响 ——
**第 201 层入场和第 1 层花一样的 gas**（有测试断言）。

有一条 fuzz 测试让 owner 随机乱挪 256 轮，每轮结束都检查：所有人仍然走得到 ROOT、没人走进环里、成员数不变。

### 层级是算出来的，不是存的

挪动一个人，他下面整条线的层级都会变。存起来的数字会悄悄过期，所以 `levelOf` 每次沿树往上数。
为了不让查询无限跑，往上最多走 512 层（`MAX_LEVELS`），超过就拒绝回答 —— 真实推荐链远到不了这个深度。
